# ADR-004：试验区渲染架构 —— Canvas 图形 + HTML UI 混合，完整 Canvas 化后置

> 日期：2026-10-07 | 状态：已拍板（yiyi 建议，用户待确认）| 范围：v1 视觉重设计及以后

## 背景

用户在对标「粒子先生」桌面端实验台时提出疑问：数形的「试验区」（图像实验台）
是否应该整体 Canvas 化（曲线、坐标轴、公式、读数、按钮全部画进一块 Canvas）？

粒子先生的实验台确实是一整块 Canvas（拟物仪器：游标卡尺、旋钮、读数窗），
而数形当前是混合架构：曲线/坐标轴/网格由 Canvas 绘制，公式 badge、
关键点放大窗、实时读数条、控制按钮均为 HTML/DOM。

## 决定

**v1 保持「Canvas 图形 + HTML UI」混合架构；「完整试验区 Canvas 化」后置为 v2 候选，
不进入 v1，由真实用户反馈驱动是否立项。**

- Canvas 负责：坐标系、网格、曲线、标注点、特殊线（对称轴/渐近线）、k 几何矩形。
- HTML/DOM 负责：图内实时公式 badge、关键点放大窗、关键点读数条、滑杆、
  状态 chip、探究三步、铁律等一切文字与交互控件。

## 理由

1. **文字清晰度与无障碍**：公式、读数是教学内容的核心载体。HTML 文字天然清晰、
   支持缩放与屏幕阅读器；Canvas 内手绘文字在缩放与高分屏下发虚，且无障碍成本高。
2. **v1 目标是视觉重设计**：数学渲染层刚在 v0 完成验收（F1–F8 全过、控制台 0 error），
   此时重构交互架构属于换引擎而非换皮肤，风险收益比不划算。
3. **对象不同，架构不必相同**：粒子先生需要整块 Canvas 是因为其对象是拟物仪器
   （旋钮/卡尺必须整体绘制才有质感）；数形的对象是数学图形 + 教学排版，
   「图形 Canvas + 排版 HTML」是更对口的架构（如 Desmos 同样采用混合方案）。
4. **演进路径清晰**：混合架构不堵死未来。若 v2 要做「直接拖拽顶点/关键点」这类
   Canvas 级交互，可在现有 Canvas 层上增量加 hit-testing，无需推翻 HTML 层。

## 后果

- v1 编码 agent 不得把公式/读数/按钮画进 Canvas；PRD F1、F9b 的验收项均按混合架构走查。
- v2 若立项「拖拽关键点」，需另写 ADR 评估 hit-testing、触摸手势与无障碍回退方案。

## 否决的备选

- v1 直接整体 Canvas 化：重构量大、文字清晰度与无障碍倒退、且无真实用户反馈证明
  混合架构不够用，否决。
- HTML 画曲线（SVG/DOM 模拟）：60fps 拖拽性能不达标，否决（v0 已验证 Canvas 路线）。
